Connected Accounts

A data model that separates 「誰登入了」（platform SSO, OAuth, whoever's session) from 「這個平台後台可以讀哪個廣告帳戶」（campaign sync). Meta 跟 TikTok 的帳戶連結體驗爛， 是它們的問題；只要這一層設計對了，就不會變成我們的問題。

§01

問題出在哪一層

「帳戶連來連去，有時候還找不到」——這句話背後通常是同一個根因：廣告帳戶的存取權，被綁在某個人的登入狀態上。 那個人換密碼、被登出、離職、Facebook 突然要求重新驗證，token 就跟著死掉，而且死掉的時候往往 沒有清楚的錯誤訊息，只是「找不到帳戶」。

這不是我們能修好 Meta 或 TikTok 的 SSO——那是它們的產品問題。但我們可以決定：連線這件事， 在踏進我們自己的系統之後，要不要繼續依賴那個脆弱的個人登入狀態。答案應該是不要。

§02

兩種連線方式：脆弱 vs. 穩固

同一件事（讓我們的系統存取一個廣告帳戶）可以用兩種方式做到，差別在token 綁在誰身上。

Meta

Business Manager 底下建 System User，發長效 token。需要 Business Verification，但一勞永逸。

Google Ads

用 MCC（Manager Account）+ Service Account 存取底下客戶帳戶，不綁單一 Google 個人帳號。

TikTok

App 層級申請 Advertiser 存取權，換到的 long-term access token 綁在 App，不綁登入的人。

Snapchat

Organization 層級的 OAuth app，token 綁 Organization。同樣避免個人登入依賴。

§03

ConnectedAccount 欄位

這張表是整個模型唯一的「單一事實來源」——任何 campaign 資料要同步，都得先查到這張表裡狀態是 connected 的一列。

欄位用途
platformgoogle_ads / meta / tiktok / snapchat
platformAccountId該平台上的廣告帳戶 ID（不是使用者 ID）
authMethodsystem_user / service_account / oauth_user——決定穩不穩
statusconnected / needs_reauth / disconnected
accessToken / refreshToken加密存放，只在 server 端解密使用
tokenExpiresAtSystem User 型 token 通常是 null（不過期）
connectedByUserId稽核用——誰當初按下連線，不代表資料存取依賴這個人
lastSyncedAt / lastSyncError壞掉的時候第一眼就看得到，不用去猜
§04

內部 → 外部，資料模型不用重寫

現在 Organization 就一筆（自己公司），所有 ConnectedAccount 掛在這筆底下。 之後要轉外部給其他 agency 用，多開幾筆 Organization、每個客戶登入後只看得到自己的 ConnectedAccount 跟 Campaign——資料表結構完全不用動，要加的是「使用者屬於哪個 Organization」跟登入系統。這是 Lark 那條路真正值得先做對的地方：不是為了現在的多租戶，是為了以後不用重寫。

現在該做的，只有這件事：把現有 Campaign 的 platform 字串欄位，換成指向 ConnectedAccount 的關聯。其他（System User 設定、多 Organization）都等真的要接平台、要對外開放時再做。
